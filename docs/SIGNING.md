# Подпись Windows-клиента

Windows 11 Smart App Control («Интеллектуальное управление приложениями») не запускает программу, издателя которой не может подтвердить. В окне блокировки нет кнопки «всё равно запустить», у него нет списка исключений, и снять блокировку только для одного приложения нельзя. На этой машине функция включена в боевом режиме, поэтому `Netlane.exe` на ней не стартует.

Решение ровно одно: **подписать наши исполняемые файлы сертификатом, которому Windows доверяет**. Отключать Smart App Control не нужно и не рекомендуется — он выключится навсегда, вернуть его можно только переустановкой системы.

## Что подписывается

| Файл | Кто подписывает | Почему |
| --- | --- | --- |
| `Netlane.exe` | **мы** | Основное приложение, именно его блокирует Smart App Control |
| `NetlaneTests.exe` | **мы** | Встроенные тесты сборки; без подписи не запускаются на машине с включённой функцией |
| `engine/trusttunnel_client.exe` | AdGuard Software Limited | Официальный закреплённый движок уже подписан, подпись не трогаем |
| `engine/trusttunnel_client.exe` (routed) | **мы** | Собственная сборка движка из закреплённых исходников без подписи; Smart App Control проверяет и дочерний процесс |
| `engine/wintun.dll` | WireGuard LLC | Подписан издателем, не трогаем |

`Netlane.exe.config` подписывать не нужно: это не исполняемый файл, Smart App Control его не проверяет.

Скрипт подписи сам пропускает всё, что уже имеет действительную подпись, поэтому движок AdGuard и `wintun.dll` остаются с подписями своих издателей, а собственный routed-движок подписывается.

## Какой сертификат нужен

| Вариант | Запускается у всех сразу | Что нужно от каждого пользователя | Стоимость |
| --- | --- | --- | --- |
| **Самоподписанный** | нет | один раз установить наш `.cer` | бесплатно |
| Microsoft Trusted Signing (Azure) | да | ничего | подписка Azure, проверка организации |
| EV code signing | да | ничего | дороже остальных |
| OV code signing | не всегда: репутация набирается | ничего | средняя |

### Самоподписанный: что именно проверено

Проверка на этой машине с включённым Smart App Control, на настоящем `Netlane.exe` из `Desktop\Netlane`:

| Вариант | Результат |
| --- | --- |
| `Netlane.exe` как есть, без подписи | заблокирован |
| те же байты, подписанные самоподписанным сертификатом, которому пользователь доверяет | **запустился** |

Дело не в «доверии Microsoft», а в том, знает ли Windows сертификат. Если он добавлен в доверенные корневые текущего пользователя, подпись становится действительной, и Smart App Control приложение пропускает.

Плата за такой вариант — **каждый пользователь один раз устанавливает наш сертификат**. Это неудобно и создаёт реальный риск: сертификат в доверенных корневых может подписывать любые программы, а не только Netlane. Кто получит закрытый ключ, сможет выпускать код, которому эти пользователи доверяют. Ключ храните отдельно от репозитория и от чужих резервных копий.

Учтите и вторую проверку: Smart App Control и SmartScreen — разные механизмы. Самоподписанный сертификат снимает блокировку Smart App Control, но при скачивании из интернета Windows может ещё показывать «Windows защитила ваш компьютер»; это лечится кнопкой «Подробнее» → «Выполнить в любом случае» и со временем проходит.

Начиная с 2023 года сертификаты для подписи кода выдают с закрытым ключом на аппаратном носителе или в облачном HSM, поэтому файл `.pfx` — редкий случай: режим `-PfxPath` оставлен для внутренних сертификатов и для выгрузки самоподписанного ключа, когда подписывать нужно на другой машине.

## Самоподписанный: порядок действий

### Один раз создать сертификат

```powershell
powershell -ExecutionPolicy Bypass -File clients\windows\new-signing-cert.ps1
```

Скрипт создаёт сертификат, оставляет закрытый ключ в вашем хранилище и выгружает публичную часть в `artifacts/Netlane-code-signing.cer`. Отпечаток из вывода нужен для сборки. Повторный запуск переиспользует существующий сертификат; `-Force` создаёт новый, но тогда прежние сборки придётся подписать заново.

### Подписать сборку

```powershell
powershell -ExecutionPolicy Bypass -File clients\windows\build.ps1 -DownloadEngine -Sign -SignThumbprint <отпечаток>
```

Или задать `NETLANE_SIGN_THUMBPRINT` и запускать `scripts\build-local.ps1 -Client -Sign`.

### Отдать пользователям

Вместе с ZIP отдавайте `Netlane-code-signing.cer` и скрипт `trust-signing-cert.ps1`. Пользователь один раз выполняет:

```powershell
powershell -ExecutionPolicy Bypass -File trust-signing-cert.ps1 -CerPath .\Netlane-code-signing.cer
```

Права администратора не нужны: сертификат ставится в профиль пользователя. Отменить — тот же скрипт с `-Remove`.

Без этого шага ничего не изменится: неподписанная и подписанная-но-неизвестная сборки блокируются одинаково.

### Проверить

```powershell
powershell -ExecutionPolicy Bypass -File clients\windows\sign.ps1 -VerifyOnly -Path artifacts\windows\Netlane
```

Затем запустите клиент на машине с включённым Smart App Control — это единственная проверка, которая что-то доказывает.

Отдельно стоит помнить: если сертификат утекал или использовался для нежелательной программы, его отзывают, и подпись перестаёт помогать.

## Как подписать

Сертификат устанавливается в хранилище пользователя или компьютера, после чего:

```powershell
# Подпись сертификатом из хранилища
powershell -ExecutionPolicy Bypass -File clients\windows\sign.ps1 -Thumbprint 1A2B3C4D5E...

# Сертификат в хранилище компьютера
powershell -ExecutionPolicy Bypass -File clients\windows\sign.ps1 -Thumbprint 1A2B... -MachineStore

# Проверка без подписи: что уже подписано и что нет
powershell -ExecutionPolicy Bypass -File clients\windows\sign.ps1 -VerifyOnly
```

Сборка подписывает клиент сама:

```powershell
# Только клиент, с подписью сертификатом из хранилища
powershell -ExecutionPolicy Bypass -File scripts\build-local.ps1 -Client -Sign

# То же, но с отпечатком явно
$env:NETLANE_SIGN_THUMBPRINT = '1A2B3C4D5E...'
powershell -ExecutionPolicy Bypass -File scripts\build-local.ps1 -Client -Sign

# Напрямую, минуя build-local
powershell -ExecutionPolicy Bypass -File clients\windows\build.ps1 -DownloadEngine -Sign
```

Порядок внутри `build.ps1` важен: подпись выполняется **до** запуска встроенных тестов, потому что на машине с включённым Smart App Control неподписанный `NetlaneTests.exe` тоже не запустится, и **до** упаковки в ZIP, поэтому в архиве уже лежит подписанный `Netlane.exe`, а SHA256 считается от архива с подписью.

### Microsoft Trusted Signing

```powershell
powershell -ExecutionPolicy Bypass -File clients\windows\sign.ps1 -AzureTrustedSigning `
    -TrustedSigningDlib C:\tools\Azure.CodeSigning.Dlib.dll `
    -TsaEndpoint https://eus.codesigning.azure.net `
    -CodeSigningAccount <учётная запись> `
    -CertificateProfile <профиль>
```

Библиотеку `Azure.CodeSigning.Dlib.dll` даёт пакет `Microsoft.Trusted.Signing.Client`; её можно получить через NuGet или из документации сервиса. Подписи всегда проставляются меткой времени (по умолчанию `http://timestamp.digicert.com`), поэтому они остаются действительными после истечения сертификата.

### Переменные окружения для автоматических сборок

| Переменная | Назначение |
| --- | --- |
| `NETLANE_SIGN_THUMBPRINT` | Отпечаток сертификата в хранилище |
| `NETLANE_SIGN_PFX` | Путь к `.pfx` |
| `NETLANE_SIGN_PFX_PASSWORD` | Пароль `.pfx` |
| `NETLANE_SIGN_DLIB` | Путь к библиотеке Microsoft Trusted Signing |
| `NETLANE_SIGN_TSA` | Адрес службы меток времени |

## Как убедиться, что всё получилось

```powershell
powershell -ExecutionPolicy Bypass -File clients\windows\sign.ps1 -VerifyOnly -Path artifacts\windows\Netlane
```

Скрипт печатает состояние и издателя для каждого файла и завершается с ненулевым кодом, если что-то осталось неподписанным. Дополнительно проверьте подпись в свойствах файла: вкладка «Цифровые подписи» должна показывать издателя и метку времени.

Окончательная проверка — запуск на машине, где Smart App Control включён. Локально подпись может выглядеть действительной и при этом не снимать блокировку, если сертификату не доверяет система.

## Если подпись есть, а приложение всё равно блокируется

Наблюдаемое поведение и то, как из него выходить. Случай из практики: сборка была подписана и подпись проверялась как `Valid`, но приложение не запускалось — в журнале `Microsoft-Windows-CodeIntegrity/Operational` событие 3077 с текстом «did not meet the Enterprise signing level requirements».

Что выяснилось:

| Файл | Результат |
| --- | --- |
| та же сборка без подписи | заблокирован |
| та же сборка, подписанная и **уже отклонённая** Windows | блокировка остаётся, хотя подпись `Valid` |
| та же сборка, переподписанная заново (новый хеш) | **запускается** |
| свежая подпись другим ключом, с меткой времени и без | **запускается** |

Вывод: **вердикт закрепляется за конкретным хешем файла**. Если файл однажды получил отказ, повторная проверка подписи этого не изменит — помогает только новый файл: переподписать (снять подпись и подписать снова) или пересобрать.

Почему первый файл получил отказ, достоверно установить не удалось. Наиболее правдоподобное объяснение — первая попытка запуска пришлась на момент, когда Windows ещё не подхватил только что добавленный сертификат, и отказ закрепился за хешем. Поэтому порядок важен: **сначала установить сертификат, потом распаковывать и запускать**. Если пользователь запустил приложение до установки сертификата и получил отказ, повторный запуск того же файла может остаться заблокированным — нужен файл с другим хешем.

Как переподписать конкретный файл:

```powershell
signtool remove /s artifacts\windows\Netlane\Netlane.exe
powershell -ExecutionPolicy Bypass -File clients\windows\sign.ps1 -Path artifacts\windows\Netlane -Thumbprint <отпечаток>
```

`sign.ps1` намеренно пропускает файлы с уже действительной подписью, поэтому без снятия подписи он ничего не изменит.

**Это главный практический довод против самоподписанного варианта.** Поведение зависит от вердикта по хешу, который вы не контролируете; у части пользователей первый запуск может остаться заблокированным, и лечится это только новой сборкой. Если нужна предсказуемость, берите сертификат публичного УЦ.

## Что остаётся за рамками

- **Репутация.** Даже правильно подписанная сборка может быть заблокирована у части пользователей, пока издатель не набрал репутацию. С EV-сертификатом и Microsoft Trusted Signing этого обычно не происходит.
- **SmartScreen при загрузке.** Подпись снимает предупреждение «неизвестный издатель» по мере набора репутации; SHA256 в файле `.sha256` остаётся полезным независимо от подписи.
- **Серверная часть.** Файлы для Linux (`.deb`, `trusttunnel-dev.tar.gz`) подписью Authenticode не покрываются: там проверяется SHA256, а `.deb` при необходимости подписывается отдельно (`dpkg-sig`, `debsigs`).
